REST API v1 on nhttpd

What it is

Beside the control API under /control/, nhttpd answers a described, versioned REST API under /api/v1/. The routes, their parameters and their answers are declared as data in src/httpd/ep/; the router in src/httpd/router.cpp binds and checks a request against those declarations, and the OpenAPI 3.1 document at /api/openapi.json is written out of the same tables, so the description cannot drift from what is served. The layer is taken over unchanged, as compatible forks carry it; the server beneath it is nhttpd, not the dedicated server of those forks, and /control/ stays what it was, byte for byte.

Addresses

GET /api/openapi.jsonthe document; gzipped when the caller's Accept-Encoding takes it
/api/v1/system/...the box, standby, reboot, shutdown, restart, the daemons
/api/v1/channels..., /api/v1/bouquets..., /api/v1/zap, /api/v1/modethe channel lists, the bouquets and their editing, the logos
/api/v1/epg...the guide: what is on, a channel's schedule, a search
/api/v1/timers..., /api/v1/recordings...the timers and their making, what has been recorded
/api/v1/osd...volume, mute, messages on the screen, the remote's keys
/api/v1/settings...the declared settings, their schema, reading and writing them
/api/v1/storage...mounts, directories, the files on them, network shares
/api/v1/tuner..., /api/v1/plugins..., /api/v1/config...the signal, the plugins, the configuration files

What each route takes and answers is in the document; read it from the box or build it without one: make -C src/httpd openapi-dump writes the same bytes the route answers. Seventeen of the nineteen tables known from compatible forks are served, sessions, the event stream and the server's own table among them; the two relay tables (stream, web-TV) follow with the transport work they need.

Since slice 3 the box asks for a login. POST /api/v1/login takes {"user","password"} - the pair migrated out of nhttpd.conf on the first start - and answers the session cookie (HttpOnly, SameSite=Lax) with the CSRF header's name and value beside it; every request that changes something carries the cookie and that second token. Readers on the networks lan_read names (as shipped: the loopbacks, the RFC1918 ranges and the ULA prefix fc00::/7) read without presenting anything; everyone else is answered 403, deliberately never a 401 that would put a browser's Basic popup in front of the login. Programs present a configured token as Authorization: Bearer instead; an address may carry the scoped media token (POST /api/v1/token/media) as ?token=, worth the media roots and nothing else. This is the flow that boxes with a compatible fork speak for remote timers, so such a box can drive this box's timers over /api/v1.

GET /api/v1/system/webserver answers where this server really answers - the port is the one nhttpd bound - and the PUT moves it: the answer says first what the change means for the caller (the address under the new port, whether a restart is coming), then the webserver thread is stopped, the layer's configuration reloaded, the port and address written into nhttpd.conf and the thread started again. Sessions survive the move; the program is not restarted. nhttpd also speaks PATCH now (the settings section write), refused outside /api/ exactly as PUT always was.

GET /api/v1/events is the box's own events as they happen (text/event-stream): zap, mode, standby, volume, mute, record start and stop, timer, EPG, bouquet and settings changes. The stream opens with a retry: field spread across clients, carries a comment frame when it has been silent, and runs on the connection it arrived on - no Content-Length, the body ends when the connection closes. At most eight streams are carried at once; the ninth caller gets a 503 with a Retry-After. A peer that stops reading is dropped once its backlog passes a quarter megabyte rather than buffered forever.

The settings the tables declare are this tree's: a row is only there when this program loads the key and something reads the member, and a declared default is the one this program falls back to. Rows that compatible forks declare for features this tree has stilled are carried in settingsundeclared.cpp with their reasons instead of being served.

GET /api/v1/system/legacy-usage answers with real counts: nhttpd's own /control/ dispatcher (CControlAPI) seeds the known names and counts every name it is asked for, missing ones included, so the route answers the question it exists for - whether everything has moved off the copied surface. Counted behind nhttpd's authentication: a caller the password gate turned away is not in the counts.

The TypeScript shapes of the API are written out of the document by test/web/openapi-types.js, taken over unchanged, as compatible forks ship it: node test/web/openapi-types.js openapi.json api.d.ts. Nothing generated is committed; a page that wants the types runs the generator against the document its build produced.

Answers

JSON, by length. A refusal is an RFC 9457 problem document (application/problem+json) with type, title, status and detail; the router answers 404 for a path it has no route for, 405 with Allow for a method the path does not take, 400 for a parameter or body it will not bind, 501 for a method nhttpd cannot name. Every answer carries Cache-Control: no-store, X-Content-Type-Options: nosniff and Vary: Cookie, Authorization. Answers are HTTP/1.0 with Connection: close, like everything nhttpd sends.

An answer that is a file (a channel picture, a stored file, later a recording) is sent straight out of its descriptor, whatever its size, and takes one Range: a stretch inside the file is 206 with a Content-Range, a header nothing can be made of is the whole file, and a stretch the file does not hold is a 416 problem document whose Content-Range: bytes */length says what there is to ask for. HEAD answers with the stretch's headers and no body.

Requests

GET, HEAD, POST, PUT and DELETE. A POST or PUT body is JSON, read by its Content-Length up to 1 MiB; above that the request is refused with 413, and the body is read and dropped (up to 16 MiB) so the refusal reaches the caller instead of a reset. A body the server cannot frame (two differing lengths, a length that is not a number, any Transfer-Encoding) is 400; one that stops arriving is 408 after ten seconds. 100 Continue is sent only when the client asks for it with Expect. OPTIONS and PATCH are not read by nhttpd yet and answer 501. Outside the API namespace nhttpd refuses PUT, DELETE and TRACE as it always has: a 501 line and a close without reading the rest of the request, which a client sees as a reset.

Access

What nhttpd checks: its own Basic authentication (mod_auth in nhttpd.conf), for every path it serves, and only when mod_auth.authenticate is on. With it off every route here is open to any caller that reaches the box, as /control/ has always been. The document says exactly that (scheme basic); the levels the routes declare (read, write, system) are recorded in the document as x-auth-level and start to be enforced with the session layer.

What is not there yet

  • sessions, tokens, per-route levels: the session layer, and with it the auth table and the webserver table, as compatible forks have them
  • the stream and web-TV relays (/api/v1/stream..., /api/v1/webtv...): they hand a long-lived connection to a program or a remote server; a route that would answer with one is refused with 501 until that path exists

Where things are

src/httpd/the layer: declarations, router, generator, route modules, stubs standing in for the dedicated server of compatible forks
src/httpd/nhttpd_bridge.cppthe hook that hands nhttpd's requests to the layer and its answers back
src/nhttpd/yhttpd_core/what the core grew for it: the API namespace (registerApiPrefix), the API body reader, the api-mode header, exact socket I/O
test/unit/httpd/, test/unit/nhttpd/the tests: the generator against the dump, the bridge with a filled hook handler, the core pieces over a socket pair
