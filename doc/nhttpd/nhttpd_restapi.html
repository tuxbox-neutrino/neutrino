The API layer in nhttpd

nhttpd answers the HTTP API under /api/v1/ through a layer of its own in src/httpd/. This page is for people who work on that layer: how a route is declared, how nhttpd hands a request over, and what the transport accepts and sends.

To use the API, start with the overview. Every route, with its parameters, answers and refusals, is in the reference.

Routes are data

Each group of routes is a table with one row per route. A row names the method, the path, the access level, the parameters and where each is carried (path, query or body), the shape of the answer, the refusals the route declares, and the handler. Most tables are in src/httpd/ep/; the event stream has its table in src/httpd/events.cpp, and the document's own route is in src/httpd/doc/openapi.cpp.

The router in src/httpd/router.cpp matches a request against the tables and checks the caller's access level. It then binds and checks every parameter and body member against the row before the handler runs, so a handler only sees values its row allows. A path no route has is answered 404, a method the path does not take is 405 with an Allow header, and a parameter or body the router will not bind is 400.

The tables are checked when nhttpd starts. If they fail the check, nhttpd runs without the API layer and logs the reason once.

The timer routes are also what the remote-timer screen of another box uses to drive this box's timers. Its client is kept in test/unit/interop/peer/, and test/http/check-remotebox.sh runs it against a box, so a change to the timer routes can be checked against that client.

A setting kept in the settings file gets a row only for a key Neutrino reads there, and the row names the member that key is loaded into; unit cases hold the table to both. A few rows stand for a value a daemon holds, or for one bit of a mask, and have no key in that file. Members of the settings without a row are listed, each with the reason, in src/coreapi/settings/settingsundeclared.cpp.

The document

src/httpd/doc/openapi.cpp writes the OpenAPI 3.1 document at /api/openapi.json from the same tables, so it describes exactly the routes the build serves. It goes out gzipped when the request's Accept-Encoding allows it. To get the document without a box, run make openapi-dump in src/httpd of a build tree; it writes openapi.json there and refuses when the tables fail their check.

A copy is kept in the source tree as doc/api/openapi.json, laid out one member per line, so a change to a route shows in a diff as the lines that changed. make check fails when the copy differs from the document the build writes, and make -C src/httpd update-api-doc writes it again. A build that writes a reduced document by design, or cannot run the comparison, such as a cross build, says so and skips it. doc/api/build-site.py builds the reference from that copy. node test/web/openapi-types.js doc/api/openapi.json api.d.ts, run in the source tree, writes TypeScript declarations from the kept copy; nothing it writes is checked in.

How nhttpd hands a request over

src/httpd/nhttpd_bridge.cpp registers /api/v1, with everything below it, and /api/openapi.json with the core of nhttpd as API addresses. A request to one of them is read the way Requests describes and handed whole to the layer; the answer goes back the same way. Every other path, /control/ included, stays with nhttpd's own handlers.

Access

The box has one account, kept in nhttpd-access.conf as a name and a stored form of the password. Two gates use it. The layer reads it directly, and nhttpd's own login asks for it through src/httpd/login_bridge.cpp, so a changed password is in effect for both at once.

  • Before either gate, a hook attached ahead of every other (CAuthorityGate in src/httpd/nhttpd_bridge.cpp, the rule in src/httpd/authority.cpp) asks whether the Host header names this box: an IP address, a name of a single label (localhost among them), one label under .local or under a domain /etc/resolv.conf searches, the box's host name, or a name in the allowed_hosts line of nhttpd-access.conf. A request without the header passes. Any other name is answered 400 before anything else looks at the request: on an API address with the problem document no-authority, elsewhere with a short page in plain text. So are two Host headers in two spellings.
  • The layer's gate guards the API addresses. Every route declares an access level, which the document states as x-auth-level.
  • nhttpd's own login (mod_auth) leaves the API addresses alone. While mod_auth.authenticate is on, it guards the other paths, except for the files the pages need before anyone signs in and, while no proxy is configured, calls from the box itself and the addresses mod_auth.no_auth_client names. A trusted_proxies line in nhttpd-access.conf counts as configured also when it is empty or cannot be read, and so does a file that cannot be read at all, as for the layer's reading without a password: behind a proxy every request arrives from the proxy's address. It accepts the session that the API login opens, and Basic authentication against the same account. The nhttpd.conf the image installs has it off, and then those paths answer without credentials, except for a change to the account (below).
  • On the paths that change the box with a GET (/control/, /cgi-bin/, /fb/, /api/v4/ and /y/), and for a request with an execute parameter, the session counts only when the request comes from a page of this box: Sec-Fetch-Site: same-origin, or else an Origin or Referer naming this host. Basic authentication from a browser, a User-Agent that starts with Mozilla/, is held to the same rule: without that evidence the request is answered 403 with a short text saying to open the address from the web interface. A script that sends a browser's User-Agent, as PowerShell does, is a browser here: it passes with a User-Agent of its own or an Origin header naming the box. Basic authentication from any other client counts as before.
  • One GET of the layer starts something: GET /api/v1/stream/browser/{id} runs a converter and may switch the TV picture. Signed in with the session cookie, it needs the evidence of the rule above, the session's X-CSRF-Token header, which the web interface's player sends with the fetch of a picture, or a ticket of that session for its path in the query (ticket=), which the player's audio element carries for radio; otherwise it is answered 403 not-permitted before anything starts. The page asks for the ticket with POST /api/v1/session/ticket, which carries the header as every change does; the ticket stands for that path alone, for 60 seconds, and only beside the cookie of that session, and the router takes it out of the query before it compares names. It ends with that session and with a change of the user name or the password, also for the session that made the change and goes on under new tokens. A bearer token needs none of this, and a HEAD, which starts nothing, is not asked.
  • A change to the account over /control/config?config=nhttpd (mod_auth.username or mod_auth.password, also written with _dot_) is taken only from a page of this box, by the rule above, and only with Basic authentication against the account, a session, or from the box itself: the loopback, while no proxy is configured. A trusted_proxies line in nhttpd-access.conf counts as configured also when it is empty or cannot be read. mod_auth.authenticate changes none of this, and an address that mod_auth.no_auth_client names is not enough. While the box still waits for a password of the owner's own, every such change is refused with the answer the API gives a caller signed in then, which points to PUT /api/v1/account/password. A refused request writes nothing.

Requests

nhttpd reads GET, HEAD, POST, PUT, PATCH, DELETE and TRACE. Any other method, OPTIONS included, is answered 501 before the layer sees the request. TRACE is answered 501 on every path. Outside the API addresses, PUT, PATCH and DELETE are answered 501 as well.

On an API address:

  • Header lines that together pass 64 KiB, or that have not all arrived after 10 seconds, are answered 400.
  • A body is read only for POST, PUT and PATCH, by its Content-Length, up to 1 MiB. A larger one is answered 413. Up to 16 MiB of it is read and dropped first, so the answer reaches the caller instead of a reset.
  • A body the server cannot frame is answered 400: a second Content-Length, a length that is not a number, any Transfer-Encoding, or a body on another method.
  • A body that has not arrived in full after 10 seconds is answered 408.
  • 100 Continue is sent only when the request asks for it with Expect.

Answers

A refusal the layer writes is a problem document (application/problem+json, RFC 9457) with type, title, status and detail. Of the refusals under Requests, all except the 413 come from nhttpd's request reader before the layer sees the request: the 400 for the header or the body framing, the 408 and the 501. They are a status line and headers, with no body. Every answer the layer writes carries X-Content-Type-Options: nosniff, a Vary header that names Cookie and Authorization, and Cache-Control: no-store unless the route sets its own. The refusal of a Host that names another box (see Access) is written the same way, also where it is the page in plain text. nhttpd answers in HTTP/1.0 with Connection: close, one request per connection.

An answer that is a file, such as a channel logo, a stored file or a recording, is sent from its descriptor, whatever its size, and honors one Range:

  • A stretch inside the file is answered 206 with a Content-Range.
  • A header that cannot be read, or one that names several stretches, gets the whole file.
  • A stretch the file does not hold is a 416 problem document whose Content-Range: bytes */length says what there is to ask for.

HEAD answers with the headers a GET would get and no body.

Answers that stay open

A route can also answer with a program to run, whose output is the body (a channel played in a browser), with an address to relay (WebTV), or with the event stream. All three outlive the handler. src/httpd/carry.cpp runs each on a thread of its own, on a copy of the connection, until the far end stops reading, whether or not nhttpd runs connection threads (webserver.threading).

GET /api/v1/events is a stream of Server-Sent Events. It has no Content-Length; the body ends when the connection closes. The layer carries at most sse_max_streams of them at once: 16 by default, up to 64. One more is answered 503 with a Retry-After, before a thread is started for it: a stream's place is taken before its thread, so a burst of requests starts no more threads than there are places, and with sse_max_streams=0 none at all. Each stream costs a thread whose stack reserves 512 KiB of address space, of which only the pages it touches are memory. A client that stops reading is dropped once 256 KiB are waiting for it, or once nothing could be written to it for 30 seconds. A client that is gone without closing, such as a phone that left the network, frees its place after about 80 seconds: the 20-second heartbeat and the 60-second TCP user timeout of the stream's socket.

Where things are

src/httpd/ep/
the route tables and their handlers, one file per group
src/httpd/router.cpp
matching, the access check, binding and checking the parameters, the check of the tables
src/httpd/auth.cpp, webconfig.cpp, login_bridge.cpp
sessions and tokens, the layer's configuration with the account, and the way nhttpd's own login asks for it
src/httpd/authority.cpp
the names a request may reach the box under, which the first hook asks
src/httpd/doc/
the document's writer and the openapi_dump program
src/httpd/nhttpd_bridge.cpp
the hook that refuses a request under another name, and the hook that hands nhttpd's requests to the layer and its answers back
src/httpd/carry.cpp, livestream.cpp, webtv.cpp
answers that stay open: a program's output, a relayed stream
src/httpd/events.cpp
the event stream
src/httpd/stubs/
what the layer asks of a web server (server.h, static.h), answered for nhttpd
src/nhttpd/yhttpd_core/
what the core of nhttpd does for the layer: the API addresses (registerApiPrefix), the request reader for them, exact socket I/O
src/coreapi/
what the handlers call to read and change the box
doc/api/
the kept copy of the document, its layout script and the site builder
test/unit/httpd/, test/unit/nhttpd/
unit tests of the layer, the bridge and the core pieces it uses
test/unit/support/run-tests.sh
runs the suite and names the cases it leaves out, each with the reason
test/unit/interop/
the client another box uses for remote timers, and remotebox_client, which drives it one call at a time
test/http/
checks against a running box: check-v1.sh for the API over the wire, check-remotebox.sh for the remote-timer client
test/web/openapi-types.js
TypeScript declarations written from the document
